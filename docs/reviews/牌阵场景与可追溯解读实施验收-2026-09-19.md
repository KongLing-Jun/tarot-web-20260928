# 牌阵场景与可追溯解读实施验收

日期：2026-09-19。范围：牌阵选择、首轮解读、每日一牌、直接追问与补牌追问。沿用此前用户反馈：结论绕弯、套话多，读完仍不知道答案；本轮重点增加事实与牌位来源约束。

## 结论与当前运行状态

- 六种牌阵已经有统一的适用场景、所需背景、示例问题与解读边界，前端选择页和自动选阵共用同一份资料。
- 29 个牌位的展开说明改为象征观察范围；原始牌阵数据不变，避免连带改变 P0 提示词。
- 新候选 `p1-grounded` 已接入解读接口、流式响应、记录保存和离线评测。它将逐字引文、牌位来源与模型推论分开表示。
- **本机实际配置仍为 P0，未自动开启候选、未部署。** P1 已有的速度改进实验不能等同于新候选质量过关。
- 第二轮真实生成 12 题中 11 题完整通过协议，1 题协议错误；语义审查仍检出越界。没有完成新的对 P0 盲评，更没有达到原计划 65% 胜率门槛，因此不进入默认流量。

## 六种牌阵怎样选择

| 牌阵 | 适合的场景 | 用户需要提供 | 不适合用来做什么 |
| --- | --- | --- | --- |
| 单张牌 | 每日自省、一个具体小问题、背景较少时先聚焦 | 当前关心的问题，已有目标与限制 | 判断完整因果、确认外部结果 |
| 三张牌阵 | 已有具体事件，梳理过去、现在与后续趋势 | 已发生经过、当前进展、想知道的方向 | 补写过去经历、承诺未来日期 |
| 二择一 | 比较两个已经明确的方案 | A/B 各是什么、最重要目标、收益成本与限制 | 替用户发明选项，忽略实际收支 |
| 关系牌阵 | 结合实际互动梳理关系和沟通 | 关系背景、最近双方说了什么或做了什么、要解决的问题 | 从“对方感受”位读出确定心理或隐情 |
| 时间之流 | 已有事件经过，需要复盘影响、当前卡点和行动方向 | 事件先后、尝试过的行动、反馈与目标 | 只凭牌推算具体时间，把根源位当真实原因 |
| 凯尔特十字 | 背景充分，多个相互影响的因素需要综合梳理 | 处境、目标、现实限制、已知外部因素 | 用十张牌替代背景采集，认定未表达的潜意识 |

自动选择新增同样的约束：不因感情词就选关系阵，不因问题复杂就选十字阵；背景不足优先单张，并在理由中提示最需要补充的信息。解析失败、中断或临时错误的兜底也由三张改为单张。

边界：目前仍是模型在既有 `spreadId/reason` 接口中选择；没有新增强制问卷或暂停澄清步骤。不能声称已用程序证明某个问题一定适合某个牌阵。

## 可追溯解读实现

### 现实事实

证据表只纳入原问题、历史用户问题和最新追问，保留先后顺序与最新发言 ID。旧 AI 回答单独放置，不作为用户事实；其思考内容先被去除。

每条用户来源必须包含原文连续片段。不存在的用户 ID、找不到的引文都会拒绝。`quote` 类型正文必须与其唯一引文逐字相同。程序展示的引文会转义 Markdown，不能借引文注入章节标题。

这能验证“确实引用了用户的话”，**不能证明引文必然支持模型写出的结论**。例如从一次约定见面推成多次相处，即使引用原文真实，仍然属于语义越界。

### 符号与牌位

- 正式原牌阵用注册 `spreadId + position.id` 核对牌位，牌名与方向关键词来自本地牌库；不能靠请求自带的中文标题替换真实牌位。
- 历史补牌、本次补牌与原牌通过来源、轮次及索引分别标识。同名牌不会覆盖不同轮次的来源。
- 每张牌带有与前端相同的解释范围。`symbol` 记录仅引用牌；各牌说明每条只能绑定一个实际牌位。
- 牌位、牌名与正逆位标题由程序生成，模型只写解释正文。
- 首轮全牌位覆盖目前是提示词要求，并非程序已强制的完整性门槛；抽牌是否真正由客户端随机产生也不在本轮验证范围。

### 流式输出与持久化

候选模型输出逐行 JSON。一条完整记录通过格式、来源及顺序检查后，服务端才转换成现有 Markdown。转换位于记录器之前，客户端与历史保存接收同一份正文，不把协议 JSON 当用户回答。

解析错误、缺结束标记、截断或网络中断时，保留此前有效片段并返回失败，不伪造完成事件，也不把非法原文降级显示。记录生成进度可以维持空闲计时，但不会算成首个可见正文；总超时仍然存在。

在线仍是一次模型生成，没有增加第二次审查/改写请求。语义审查目前只用于离线验收，因此**不保证在线拦截所有事实越界**。

## 独立语义审查

新增离线审查模块，逐条检查候选主张与用户原文、实际牌位的关系：

1. 引文真实，是否仍偷加了流程进展、已完成的准备、具体原因或心理？
2. 过去位是否被写成已经发生的经历？“当前审批”是否被扩写成审批原因？
3. “可能”“象征”前缀是否掩护了具体故事？
4. 最新纠正是否被旧问题或旧模型猜测覆盖？
5. 合理的未来建议和有边界的牌面倾向，是否被错误拒绝？

模型必须对全部主张 ID 各给一次结论与具体理由。缺失、重复、未知 ID 或非法结果不算有效审查。系统明确保存 `references-only` 与独立的 `semanticModelAssessment`，不会把引用匹配升级成“事实已证明”。

## 真实调用与失败记录

使用既有开发集的 12 题筛选组，生成模型 `deepseek-v4-flash`、思考 `enabled/low`，每题一次、并发 2；审查使用 `deepseek-v4-pro`。没有读取封存 holdout 正文，没有自动重试失败样本，也没有修改私有服务配置。

| 指标 | r1 | r2 |
| --- | ---: | ---: |
| 生成题数 | 12 | 12 |
| 完整协议输出 | 10/12 | 11/12 |
| 首个可见正文 P50 | 7.735 秒 | 8.026 秒 |
| 首个可见正文 P90 | 9.506 秒 | 13.106 秒 |
| 请求结束耗时 P50 | 7.912 秒 | 9.333 秒 |
| 请求结束耗时 P90 | 10.739 秒 | 14.032 秒 |
| 有效语义审查 | 10/10 | 11/11 |
| 被审主张数 | 52 | 62 |
| 模型标记越界主张 | 0（已确认漏判） | 1 |
| 校准正负对识别 | 3/3 | 6/6 |

计时采用最近秩分位数。r1 的首正文统计只包含实际有正文的 11 题，另 1 题无正文，不能据此把缺失题算快；r2 的 12 题都有正文，其中 1 题后续中断。请求结束耗时包括失败的早停，不等于成功回答的完成时间。这是小样本开发测试，不能推断线上 P90 或对 P0 的质量胜率。

本轮实际调用共 **54 次**：24 次生成、21 次完整输出审查、9 次校准。原始清单、消息哈希、协议、Markdown、计时及审查结果保存在本机 `docs/verification/p1-grounded-20260919/`，未纳入 Git。

### r1 暴露的问题及修正

- 1 题把牌库编号当成牌位引用 ID，首条就被拦下。r2 从模型材料中移除多余的牌库编号，只保留可引用的来源 ID。
- 1 题在各牌说明后又输出行动，违反章节顺序。r2 明确进入各牌说明后不能退回行动或核心。
- 逐句复核发现“前期的细致投入和反复打磨已经完成”等现实断言，原审查模型却当成普通牌义放过。r2 加入 3 对更细微的正负校准，并要求先辨认语句在断言什么，不能用牌位或符号标签给它免责。

### r2 仍未通过的地方

- 工作室趋势题把一条记录的 `type` 写成 `advice`，而协议要求 `type=claim`。正确的前两条保留，其后中断；没有把格式错误自动改成合格回答。
- 追问轮岗进展时，模型写出：“等待结果的同时其他工作事务仍在并行”。用户没提供这个事实，审查模型指出不能从星币 2 的“多任务”直接推出；该条不能通过质量验收。
- 对合同样本逐句复核仍需警惕“信息不足与回避造成的未决”等因果措辞，不能因为改进后的裁判只标记 1 条，就宣称其余 61 条全部语义正确。
- 部分答案仍重复首段结论，逐牌边界说明也偏长；引用可追溯不自动意味着简洁、好读或更直接。

校准改进证明审查能识别这些开发诊断例，不证明可以替代人工复核。两轮的生成提示词与审查规范都不同，不能把“0 条变 1 条”解释成模型质量下降或精确改善率。

## 验证与后续启用条件

代码测试覆盖：来源隔离、原文匹配、牌位绑定、不同轮次补牌、枚举类型绕过、半条记录、截断/终止、超时进度、接口与记录器一致、每日/追问/重生成入口、评测产物和默认 P0。P0 原有冻结提示词校验保持通过。

实际执行结果：

- `npm test -- --maxWorkers=2 --reporter=dot`：88 个测试文件通过、4 个跳过；986 项通过、81 项跳过。跳过项不算验收通过。
- 首次默认并发全量运行有 4 项超时、1 项异步界面断言失败；对应 3 个文件单独在 2 个 worker 下 23 项通过，再以相同 2 个 worker 完成上述全量检查。没有放宽断言或延长测试超时阈值。
- `npx tsc --noEmit`、`npm run lint` 通过；仓库默认忽略 scripts，另用 `eslint --no-ignore` 检查本轮相关评测脚本，通过。
- `npm run build` 编译、类型检查与页面生成完成，退出码 0；但 Windows standalone 复制 `[externals]_node:path...js` 时出现 `EINVAL` 警告。没有据此宣称 standalone 发布包完整可用，发布前仍需在目标构建环境验证。
- `git diff --check` 通过。

已在真实浏览器用 390×844 视口检查牌阵选择页，二择一的说明区域与确认按钮可正常阅读、滚动与操作；这是浏览器移动布局验证，不是微信真机验收。

启用候选前仍需完成：提高协议输出可靠性、减少事实外推和重复、重新运行对 P0 的冻结盲评并保留失败分母，达到原定质量门槛后再进入独立 holdout。当前不应仅因多了引用或校准通过就切默认模型。

候选由现有私有配置项 `READING_PROMPT_PROFILE` 显式选择 `p1-grounded`；本轮没有执行这个切换。回退值为 `p0`。不要把未经验证的候选直接用于生产流量。
