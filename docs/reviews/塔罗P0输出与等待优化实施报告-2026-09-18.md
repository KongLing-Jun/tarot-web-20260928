# 塔罗 P0 输出与等待优化实施报告

日期：2026-09-18。基线提交：`aa6f0a2`。本文记录开发与本地验证结果，提交及发布状态以对应 PR 为准。模型仍为本机配置的 `deepseek-v4-flash`。

## 已实现

- **输入引导**：手动选阵与智能选阵共用提问页提示用户补充具体事情、希望解决的问题、已尝试的做法、现实限制和两个选项。不增加必填表单，不替用户虚构背景。
- **回答要求**：优先直接回应；有依据时给主张与改变判断的条件；问题对象不明时尽早澄清；减少泛用领域罗列、反复免责声明与内部写作规则外露。保留事实边界、倾诉意愿、纠正事实和行动可选机制。
- **牌位结合**：实际牌位描述进入模型输入，强化三张牌、时间之流、凯尔特十字对过去经历／原因／心理的事实约束；单牌、其余牌阵、追问、重新生成和每日牌共享公共规则。
- **消息角色**：当前版本的公共写作规则进入 `system`，任务与问题进入 `user`。旧 Agent 客户端传来的旧 prompt 和内部决策 prompt 保持原协议兼容。服务端记录 prompt 版本、模型与思考档位，便于识别历史结果来源。
- **等待优化**：采用显式 `thinking=enabled`、`reasoning_effort=low`；首个正文 chunk 立即发布，首段 UI 缓冲立即更新，后续继续节流。未削减输出 token 上限，也未用截断回复换取速度。
- **评测**：在既有工具上新增 SSE 流式评测、首正文／首个实际回答计时、usage、消息角色及哈希冻结。新增同牌面的有背景／无背景配对场景。结构规则与人工语义评阅分开，不用关键词计数冒充语义质量。

本轮没有发现已检查链路中确定的原问题／追问历史丢失；测试覆盖其保留、纠错与排除历史思考内容。这个结论不代表已经调查截图对应的线上历史请求。

## 为什么选择轻量思考

原请求未显式设置模式。DeepSeek 当前文档说明默认开启思考、默认强度 high；思考模式下 temperature 不生效，因而本轮没有以调低温度作为优化方法。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

试验过关闭思考：6 个合成样例的首个正文内容约 0.6–1.4 秒，但出现把牌义写成用户经历、虚构投递配额和计算通勤差值不准确等问题，未采用。轻量思考保留推理过程，配合事实约束和正面示例减少这些回归；没有更换模型或增加每次在线质检的第二次模型调用。

这不是“low 在所有任务上优于 high”的模型排名。模式、提示词、消息角色共同改变，本轮数据只支持当前组合的小样本比较，不能单独归因给某个参数。

另用相同最终提示词补测了 6 个 high 样例，存于 `final-high-comparison/`。其中三张牌首回答 13.8 秒、二择一 28.2 秒；倾诉样例仍把“没结果”写成“回音没来”。这次补测不足以给模型档位作普遍排名，但说明剩余事实措辞问题不能靠提高思考强度自动解决；本机最终仍保留 low，未因一次高速样本关闭思考。

## 真实模型计时

输入是固定的合成问题、牌位、牌面和方向，不是用户聊天记录。每个场景每轮一次生成，并发不超过 2。基线和最终版本各自冻结消息；最终完整批次 14 个场景，涵盖六种牌阵、纠错、直接追问、补牌、拒绝复合、只倾诉、每日牌和有／无背景配对。

计时从评测脚本发起上游请求开始，不含微信网络、鉴权、保存和页面渲染。`firstTokenMs` 是首个可见 content，可能只是标题；以下使用排除仅标题／符号的 `firstAnswerMs`。总耗时包含上游生成与本地结果写入的少量开销。

| 同题场景 | 原版首回答 | 优化后首回答 | 原版完整耗时 | 优化后完整耗时 |
|---|---:|---:|---:|---:|
| 用户纠正尚未面试 | 16.4 秒 | 4.7 秒 | 18.6 秒 | 6.4 秒 |
| 常规三张牌求职问题 | 25.3 秒 | 7.0 秒 | 27.8 秒 | 9.0 秒 |
| 每日一牌无背景 | 6.3 秒 | 1.9 秒 | 7.2 秒 | 2.6 秒 |
| 二择一 | 27.0 秒 | 22.6 秒 | 30.9 秒 | 24.5 秒 |
| **四个同题样例中位数** | **20.9 秒** | **5.9 秒** | **23.2 秒** | **7.7 秒** |

单次小样本受网络、服务负载、缓存和生成随机性影响，不能视为线上 P50/P95 或延迟承诺。最终批次的时间之流、凯尔特十字和直接追问仍分别出现约 28.1、28.2、24.8 秒的首回答等待；复杂任务长尾尚未消除。

最终批次上游返回总用量为 59,437 tokens，包含输入、正文及推理，不含前期试验。未查询实时单价，不据此估算费用。

## 输出效果与未消除的问题

最终三张牌样例开头直接给出“优先继续投当前岗位，暂不全面换方向”，依据是两周六份申请和一次邀请，再用邀请岗位与目标是否一致作为改变判断的条件。无背景的配对样例先询问具体事情，有背景版本转为结合面试、项目与两小时准备时间回应。

迭代中发现并针对性调整了以下真实输出问题：关闭思考后过度推断；从没有付费客户推断没有作品或获客入口；把旧模型建议当成用户已经完成的准备；把“没有结果”改写成“没有回应”。前两类具体的背景混淆在最终时间之流与补牌样例中改善；但最终倾诉样例仍把“没结果”改成了“没有回音”，不能视为全部修复。失败输出保留，不删除后只展示最好的一轮。

最终 14 份都完整返回，未触发 token 截断；11 份没有结构检查问题，另外 3 份仍有警告：

- `extras-1`：部分牌位标题未完整匹配现有牌位／方向格式。
- `context-specific-1`：章节不完整。
- `listen-only-1`：章节不完整。

这些输出保留原文，沿用现有提示机制；没有通过自动补写模型观点或放宽质量规则掩盖问题。结构无误也不代表语义合格。专业说明仍可能偏长、重复解释局限，个别建议仍有可收紧的条件和措辞；本轮不能宣称稳定杜绝幻觉，也没有完成原方案设想的 60 条开发集＋30 条独立留出集。

语义审阅还指出：二择一样例的“A能保住储备”比已知收支信息更肯定；关系样例个别句子把建议描述为既有互动方式。这些是当前质量限制，不能用 14 次请求成功或运行时间下降掩盖。当前改动改善了澄清时机和部分建议的针对性，仍需后续持续评测，不能据本次样本直接宣称达到全面上线质量门槛。

## 本地配置与发布注意事项

本机私有配置与示例配置已采用：

```json
{
  "MODEL_THINKING": "enabled",
  "MODEL_REASONING_EFFORT": "low"
}
```

设置由服务端读取，客户端不能覆盖。显式思考参数仅允许当前已验证的 `api.deepseek.com`，其他兼容接口不自动套用；不兼容配置会在上游请求与聊天持久化前报错。旧配置没有这两个字段时保留提供商原行为；`provider` 表示不发送扩展参数。关闭思考或使用 provider 时须删除 `MODEL_REASONING_EFFORT`。

部署需要同步业务代码和服务器私有配置；只发布前端代码不会自动修改线上私有模型参数。已经打开的旧 Agent 页面仍可能携带旧版 prompt，验证时需要刷新页面并发起新的解读，历史解读不会被改写。本轮未部署远端、未推送或提交 Git。

首字加速不改变取消、重试、保牌和持久化协议。配置获取尚没有独立于整体流程的超时，最终保存确认也可能使完成状态晚于正文结束；本轮没有改动这两处，不声称所有等待来源已经解决。

## 验证与复现

本轮执行了单元／集成回归、lint 和生产构建，并用浏览器检查了本地提问页的桌面及 390×844 移动视口。没有完成 iOS／Android 微信真机验证，也没有把直接上游评测描述成包含鉴权与保存的完整线上性能验证。

- 最终 `npm test`：75 个测试文件通过、4 个按现有条件跳过；792 项通过、81 项跳过。
- `npm run lint` 与评测脚本／测试的显式 ESLint：通过。
- `git diff --check`：通过。
- 与生产构建同时运行过一次全量测试，抽牌交互用例超过原有 5 秒上限；未放宽超时，构建完成后重跑全量通过。先前遗漏新增配置 mock 的持久化测试也已补齐并通过。
- 本地 3000 生产进程已重启，3000／3001 提问页与 4113 日牌预览均返回 200；匿名请求受保护的配置接口返回预期 401。

Windows 默认 Turbopack 构建出现 traced 文件名复制警告；`npm run build -- --webpack` 成功完成编译、TypeScript、静态页生成和 standalone 产物构建。未为此修改项目默认构建脚本或升级依赖。

真实模型结果与冻结输入保留在开发机上、本报告同目录的 `reading-p0-evaluation/`。原始生成文件未纳入本次 Git 提交，仓库读者可使用下方命令生成新的评测记录；以下为本机留存目录索引：

- `baseline-results/`：原版四份同题基线，来自修改前冻结的 prompt。
- `candidate-results/`、`low-results/`、`revised-low-results/`、`revised-high-check/`、`final-low-results/`、`coverage-results/`、`accepted-results/`：开发过程样例，目录名不表示质量通过，不能混作最终版本。

冻结与执行示例（运行会调用配置中的模型并产生费用；普通 `npm test` 不运行真实模型）：

```powershell
npx tsx scripts/evaluate-reading-output.ts --prepare --suite empathy --stream --thinking enabled --reasoning-effort low --output <新的冻结目录>
npx tsx scripts/evaluate-reading-output.ts --run --input <冻结目录> --attempts 1 --output <新的结果目录>
```

后续应保持冻结问题和牌面，增加重复次数与独立留出题，记录实际用户对“太泛／没回答／建议不可做”的反馈；在这些证据出现之前，不进一步降低思考或直接替换模型。
