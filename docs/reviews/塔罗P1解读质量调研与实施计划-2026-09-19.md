日期：2026-09-19。代码基线：`edc50df`，分支 `codex/integration-20260917`。

状态：**用户已批准实施及真实调用验收。工程实现和开发集初筛已执行，生产默认尚未切换。** 调研阶段的结论保留在下文；实际修改、实验失败和验收边界见 [P1 实施验收报告](./塔罗P1实施与真实验收报告-2026-09-19.md)。没有导出生产会话或部署线上。

用户已确认的首要问题：**“结论绕弯、套话多，读完还是不知道答案。”** 范围覆盖手动牌阵、智能对话、追问、补牌、重新生成及每日一牌，不限于每日牌。

## 1. 建议审查的结论

建议采用“复用评测工具，针对产品实现回答规范”的组合路线：

1. **P1-A：先把回答核心问题做对。** 调整回答顺序和任务区分，避免将所有问题改写成行动建议或信息收集任务。保留目前的首段流式加速。
2. **P1-B：建立用户能判别的质量验收。** 优先复用 Promptfoo 的语义评分与候选比较能力，保留项目已有的真实调用、冻结输入和 SSE 计时工具。把“开头能否读出答案”作为首要指标。
3. **P1-C：知识包和模型分别做对照实验。** 只有证明有增益的部分进入产品，不预设“安装塔罗 Skill”或“换 Pro”就能解决问题。
4. **P1-D：胜出方案小范围接入与回滚。** 覆盖所有入口；默认一次正文生成，不给每条解读加串行审稿模型。

**市场上有可复用的通用工程组件，也有塔罗专用 API 和 Skill；本次没有找到经过中文用户体验验证、可以直接替代当前解读链路的成熟成品。** 这是本次检索范围内的结论，不是“市场上绝对不存在”。

建议这次批准的实现范围为：回答规范、离线评测接入、有限知识增强试验及候选模型盲测。Langfuse 全面接入、Dify 迁移、自动 Prompt 搜索、微调和在线双模型审稿暂不纳入首轮。

### 需要通过实验验证的原因

- **回答目标偏移**：现有规则可能将“给出解读判断”过度转成“提出一个安全的小动作”，造成答非所问。
- **重复表达**：核心、行动、逐牌说明分别完成类似要求，可能将同一个意思重复三次。
- **知识输入冲突**：牌义中存在“你拥有一切资源”“好运即将到来”等现实断言，但系统规则又要求不把牌义当事实；这可能增加输出摇摆。
- **模型能力或档位不足**：可能影响综合判断和语言收束，但目前没有控制变量的证据证明这是主因。

上述属于有代码或样例依据的假设，不能直接宣称因果已被证明。用户本次没有提供新的完整失败会话；仍需核对该次生成的版本及原问题，不能假定线上一定与本机完全相同。

## 4. P1 的回答目标：先回答，再解释

### 4.1 最重要的产品规则

**用户不展开各牌说明，也应从核心解读的前两句话知道回答是什么。**

核心采用自然中文表达：当前判断 → 最重要的理由 → 真正影响判断的条件。这里的顺序是验收要求，不要求每条都输出三个小标题，也不强制每题都有行动建议。

区分两种依据：用户提供的现实事实，与牌面的象征解释。牌面可以给出清楚的解读倾向，但不能被包装成已证实的他人心理、事件或统计概率。减少的是重复撤回和空话，不是事实边界。

### 4.2 按问题类型选择回答方式

| 用户在问什么 | 合格的开头 | 应避免的偏移 |
|---|---|---|
| A/B 怎么选、是否继续 | 在已知目标与约束下给当前优先项；缺少决定性条件时，直接说明哪一个条件会使选择翻转 | 罗列两边优缺点后说“看你自己”；把收入较低等同入不敷出 |
| 事情或关系的趋势 | 给出这组牌的主要象征走向及关键阻力；有现实事实时解释其对应关系 | 只给“可以观察一下”；把象征趋势说成一定会发生 |
| 对方是否喜欢、会不会联系 | 明确回答牌面是否支持用户所问的倾向，并一次说清不能确认真实心理或未来行动 | 虚构对方动机；反复免责声明后完全不解释牌面 |
| 我现在具体怎么做 | 先给一个适配已有事实和限制的做法，再解释原因 | 为凑“行动”附带一组任务；重复用户已做过的事 |
| 纠正或追问 | 首句处理最新纠正或问题，沿用原牌及有效历史 | 再写一份首轮解读；继续沿用已被纠正的判断 |
| 只倾诉、不想听建议 | 回应已说出的感受与经历 | 强迫判断、安排任务或追问未提供的信息 |
| 每日一牌 | 一句话提出当天的反思主题，再给必要解释或可选应用 | 代入未经提供的生活情节；开头要求补背景 |

只有问题对象、A/B 对应关系或真正改变回答的条件不明时才澄清。已经能回答的部分先回答；普通缺少细节不自动触发新一轮问答。若确实没有足够信息，直接说清缺口本身就是答案，不能用更长的套话替代。

### 4.3 结构与去重复

- 保留当前核心／可选行动／各牌说明协议，避免首轮引入大规模渲染改造。
- 核心只表达一次主判断。行动不重讲判断过程；各牌说明补充依据，不逐张重复建议。
- 多牌阵解释关键牌之间的支持、阻力或变化；其余牌满足完整性，但不为了“专业”创造新的情节。
- 允许在核心中用少量必要的牌面依据解释为什么这样读，避免核心看起来像与抽牌无关的通用职场建议。
- 不用简单词语黑名单处理“可能”“但是”。判断这些词是否表达有效条件，还是在无信息增量地撤回答案。
- 不要求输出隐藏推理过程；只展示面向用户、可核对的简短理由。

### 4.4 待审的表达目标示例

以下是人工编辑示例，只展示结构目标，不是新模型实测，也不会作为固定回答塞入程序。

原合成题：“两周投六份简历，收到一次面试邀请，尚无结果。应该换方向还是继续投？”

> 先继续当前方向，暂时不必全面转向。你已经收到一次邀请，仅凭尚无结果还不足以说明方向错了；如果这份岗位本身就不符合你的目标，再调整方向。

如果配合原评测的女祭司正位、女皇逆位、皇帝正位，后续简短解释它们如何构成“核对标准—检视投入—建立结构”的象征联系，而不是再把同一个求职建议写三遍。正式质量评测还必须检验是否歪曲牌义、是否真与该问题相关，不能只评开头利落。

## 5. 实现方案与复用边界

### 5.1 回答规范：先在现有单次生成内实现

复用 `buildReadingMessages` 与已有模式。把混在一起的要求拆为稳定事实边界、问题类型的回答要求、当次牌阵材料、输出协议。先删除当前任务内的重复要求，再增加必要正反例，而非在旧 Prompt 末尾不断堆规则。

不新增一个串行模型来分类所有问题。显式模式从已有字段取得，自然语言意图在同一次生成中处理；只有后续实验显示分类是瓶颈，才另行设计。

### 5.2 轻量知识包：仅作为独立实验变量

当前78牌和6牌阵规模适合按 `cardId + orientation + spreadId + positionId` 精确装配，不需要向量检索才能找到已知的牌。

候选知识条目包含核心主题、相关意象、该方向的表达、牌位作用、可采用的联系及不能推出的现实事实；附 `knowledgeVersion`、来源和审核状态。多牌关系使用少量经过审核的组合原则，避免穷举所有牌对。

优先整理项目已有数据，保持 RWS 体系与现有牌 ID。外部 Skill 只参考可兼容的方法，不照搬所有元素、数秘、宫廷对应，也不直接复制商业牌书。采用第三方内容前固定版本、核查许可并记录来源。开发机装一个 Skill 不会自动让小程序的模型 API 加载它，必须显式装配至运行时输入。

试验先覆盖评测涉及的牌；正式启用知识增强前应完成78牌双方向的内容覆盖与一致性校验。未审核或缺失时回退到明确标记的原版本，不把部分覆盖伪装成全牌升级。牌典展示文案不在本次顺手重写。

### 5.3 所有入口统一版本

普通请求、Agent、每日、追问、补牌、重生成最终使用同一版本装配。新客户端逐步提交结构化材料，由服务端选择 Prompt/知识版本；旧 `agent.prompt` 保留明确的兼容路径并记录 legacy 状态，避免假称已经使用新知识。

公共 API 采用兼容性扩展，不直接删除旧字段；不靠匹配任意旧 Prompt 文本来猜版本。保留原问题、最新事实纠正、历史补牌与实际抽牌，不重抽牌、不覆盖旧解读。内部选阵/补牌决策与面向用户的正文生成分开适配，不能误套正文结构。

### 5.4 模型对照：先证明再路由

首批比较当前配置对应的实际 Flash 模型与 DeepSeek Pro 候选，使用同一输入、相同知识、明确记录的思考档位和输出预算。其他供应商只有在这组试验无合格候选或收益有限时再扩展，不先采购多家接口。

**新核实事项**：DeepSeek 官方 2026-09-10 更新说明，`deepseek-v4-flash` 暂时路由到 V4.1 Flash，最新调用名为 `deepseek-flash`，V4 Pro 服务继续提供。历史报告中的字符串是当时的配置名，不能据此断言实际底层模型是旧版。实验应记录请求模型、响应模型、日期、参数和 Prompt 哈希；返回名仍为别名时注明无法固定快照，交错运行实验组减轻时段偏差。[官方更新日志](https://api-docs.deepseek.com/updates/#date-2026-09-10)

不把代码/数学榜单成绩当作中文塔罗写作排名，不预设 Pro 更好。若仅复杂问题有收益，再根据可验证的任务类型启用配置化路由；不只按牌数武断升级。更换供应商时显式适配能力，不能沿用 DeepSeek 专属参数。

### 5.5 评测复用与速度保护

- 保留 `scripts/evaluate-reading-output.ts` 的输入冻结、消息哈希、真实 SSE 计时和 usage；Promptfoo 通过薄适配层复用结果或调用器，不复制另一套业务 Prompt。
- 第一阶段先对保存的回答做离线评分与盲评，验证工具适配；必要时导入现有输出，避免重复付费生成。
- 评审只在离线进行。默认线上仍为一次正文生成，保留首段立即发布、取消与重试协议。
- 语义评分附原文证据；单测继续负责确定性行为。不可把结构匹配、禁词数量或 JSON 合法性当成回答质量。
- 若 Promptfoo 无法准确接入本项目 SSE 指标，仅用它做内容评测，保留现有计时器。先用固定版本验证 Windows/Node 兼容，不为工具迁移整套服务。

## 6. 实验与验收设计

### 6.1 数据集

沿用此前规划目标：**60 条开发集 + 30 条独立留出集**。这是待建立的数据规模，不是本轮已完成的数据。

以**用户的问题类型**作为主分层，而不是仅按牌阵或入口分层，避免用大量“怎么做”题掩盖判断类回答的不足。建议配额如下；每题归入一个主要类型，入口与牌型作为附加标签：

| 主要问题类型 | 开发集 | 留出集 |
|---|---:|---:|
| 是否、会不会等判断（不含下方关系心理题） | 12 | 6 |
| 趋势、事情走向、每日反思主题 | 12 | 6 |
| 对方态度、关系心理与联系倾向 | 10 | 5 |
| A/B选择、继续或转向 | 10 | 5 |
| 具体方法、执行与事实纠正 | 10 | 5 |
| 倾诉、明确不要建议 | 6 | 3 |
| 合计 | 60 | 30 |

在这些类型内交叉覆盖六牌阵、每日、追问纠错、补牌、信息不足和信息足够；四花色、宫廷牌、正逆位均有代表。首轮12条代表题每类至少2条，判断、趋势和对方态度类必须单独报告成绩。留出集预先冻结，问题与改写、同牌配对等属于同一组，不能拆到开发和留出两侧。

新增两种关键配对：

1. **同牌不同问题/事实**：判断回答是否随用户情况产生实质变化。
2. **同问题不同牌**：判断牌义解释是否有区分度；用户事实强约束结论时允许主张不变，不能为“牌不同”强迫推翻现实判断。

已看过的 P0 样例归开发/回归，不冒充新留出题。用户提供的失败会话先脱敏、核对版本；未取得时明确标注为合成数据。默认不抽取生产数据库或向新第三方上传真实会话。

### 6.2 对照组与预算

| 组 | 改变的变量 | 要回答的问题 |
|---|---|---|
| A | 冻结的 P0 基线 | 原版实际水平是什么 |
| B | A + 新回答规范及去重复 | 不换模型，能否解决绕弯 |
| C | B + 精简知识包 | 额外知识是否真提高判断与牌义联系 |
| D | B + 候选模型，知识与 B 相同 | 模型本身是否有净收益 |

先用开发集中的12条代表题、每组重复2次：最多 **96 次生成**。没有基本收益的组停止扩大；每次记录失败，不能只保留最好的一次。若 C 与 D 分别胜出，再单独预算测试其组合，不直接把两者收益相加。

选定唯一候选后，用30条留出题、基线与候选各重复2次：**120 次生成**。所列初筛与留出两阶段完整执行为216次生成，早停则更少；其余开发迭代、模型裁判、重试与组合试验另计，不能把216说成全部费用。

执行前查询实际可用模型和单价，以真实 token/推理计费方式估算预算，配置金额/调用次数上限、并发与超时，到达上限停止。当前不填未经核验的人民币金额，也不启动调用。开发集其余题用于进一步诊断，但不得偷看留出答案调 Prompt。

### 6.3 评分：围绕“读完知道答案”

各维度0–2分，所有版本同一标准：

| 维度 | 0分 | 1分 | 2分 |
|---|---|---|---|
| 直接回答 | 回避或改答另一件事 | 有结论但埋在后面、反复撤回 | 前两句回应所问；不足时明确唯一关键缺口 |
| 结论一致 | 前后矛盾 | 大致一致但限制条件混乱 | 主判断、理由与条件一致 |
| 信息效率 | 重复套话占主导 | 有重复但仍可读 | 每段提供新信息，无模板式收尾 |
| 牌面关联 | 与牌无关或错误 | 逐牌正确但整体薄弱 | 关键牌位关系支持本次解读，且不冒充现实证据 |
| 事实与意图 | 编造或违背明确意愿 | 少量过度推断 | 准确保留事实，回答方式符合本轮目的 |

行动题另评可执行性，倾诉/趋势题不因没有行动扣分。先请用户盲看至少10组代表答案，校准对“干脆但武断”“谨慎但没回答”的取舍；模型裁判随后辅助扩展，不能代替用户体验。随机打乱版本和顺序，检查交换 A/B 后裁判是否稳定。保留分歧和失败全文。

### 6.4 建议验收门槛（待本计划批准，不是已取得结果）

- 留出样本中，至少90%的输出在核心前两句得到“直接回答”2分；按问题类型另报，不用每日短答拉高总体。
- 候选相对 P0 的盲评胜率至少65%，**以全部比较为分母，平局单列**；必须报告样本数。重复生成按同一问题聚类看待，不能把60次当60个独立问题。
- 留出集中不接受已确认的严重事实编造、牌面错配或违背明确用户意图；有则返工。这是小样本发布门槛，不是线上零错误承诺。
- 用户对10组代表答案中的至少8组认可“读完知道答案”；这是偏好校准，不外推为市场满意度。
- 相同测试条件下，首个有用回答 P50 相比当前 P0 不劣化超过10%，P95 不劣化超过20%；均是建议容忍线，须在测试前冻结。小样本 P95 仅作预警，灰度后继续观察。
- 报告总耗时、token、费用、错误率和放弃率。直接上游计时与微信端到端计时分开，标题或符号不算首个有用回答。

不合格时保留 P0，不因代码完成或模型更贵而发布。留出集暴露的问题修复后，需要补充新留出样本再验收，避免把原留出变成训练集。

## 7. 执行顺序、交付物与估算

| 阶段 | 交付内容 | 验证/退出条件 | 粗略工程量 |
|---|---|---|---|
| 0：事实与评分对齐 | 核对部署版本、失败分类、样本清单、评分卡、用户盲评样例 | 明确什么算回答到位；无真实案例则标注合成局限 | 1–2日 |
| 1：回答规范试验 | B版本Prompt、去重复规则、回归样例、Promptfoo薄适配 | 小样本盲评可看出收益，否则先修标准/回答目标 | 1–2日 |
| 2：知识/模型对照 | C、D对照报告，内容来源与许可清单，耗时/费用记录 | 判断保留哪种增强；无收益就不接入 | 2–3日，另计内容审核 |
| 3：胜出方案接入 | 所有入口统一版本、兼容路径、回滚配置 | 单元/链路回归与留出盲评通过 | 2–3日 |
| 4：小范围验收 | 微信真机记录、反馈与版本关联、小范围发布建议 | 用户审阅结果，再决定是否发布 | 1–2日，依赖真机与反馈 |

合计约7–12工程日，为规划估算；60+30样本建设、78牌知识人工审核、模型调用等待与用户反馈可能拉长周期。**第一份可审查的实际回答对照应在阶段1交付，不等全部工程完成才发现方向不对。**

业务文件的主要落点：

- `lib/api/prompts.ts`：回答规范、少量示例、去重复、相关知识装配。
- `lib/tarot/cards.ts` / `spreads.ts`：复用稳定标识；新知识内容通过独立版本文件维护，避免改动牌典展示的副作用。
- `app/api/interpret/route.ts` / `lib/agent/agentTurn.ts`：服务端版本与各入口兼容；仅在胜出方案需接入时修改。
- `lib/api/server-config.ts`：模型候选及版本选择沿用配置机制，不把可变阈值、供应商地址或密钥写死。
- `scripts/evaluate-reading-output.ts` / `tests/fixtures/`：冻结实验、导出对照、内容评分和覆盖矩阵。
- `lib/interpretation-quality.ts`：保持确定性检查职责，不伪装成万能语义裁判。

## 8. 回归、发布与回滚

必须验证：知识ID/方向/牌位匹配、未知数据处理、上下文更新、取消、首段流式、补牌历史、保牌重试、持久化幂等、旧客户端、新旧版本隔离，以及内部决策不受正文Prompt影响。运行相关单测、完整测试、Lint、类型与生产构建，并执行微信内实际生成验证。

先做离线实验，后做用户审阅，再决定小范围发布。新版本的选择比例、模型路由、预算和超时使用项目配置；记录请求/响应模型、Prompt/知识版本、usage与延迟，不默认新增完整私密会话日志。反馈只关联必要的解读ID与问题类别，原文使用沿用项目隐私规则。

保留 P0 回退。失败时显示现有错误与可重试状态，不偷偷重新抽牌、悄悄替换已经流出的正文或静默升级到更贵模型。没有经过验证的模型不作为自动兜底。
