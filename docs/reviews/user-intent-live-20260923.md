## 测试范围

使用当前私有配置的 `deepseek-v4-flash`，真实请求共 10 次，其中 8 次意图提取、1 次自动选阵、1 次情绪支持解读。输入均为测试脚本内的合成场景，不读取真实用户问题。

复用应用实际提示词构建器、模型生成配置、超时、输出预算、原文引用校验和回答策略。请求为非流式调用；没有执行数据库迁移，没有修改功能开关，没有验证 HTTP 鉴权、快照持久化和完整浏览器到数据库链路。下游情绪支持使用固定测试牌面，未改变产品抽牌逻辑。

这些是单轮、少量、预设合成用例的观察结果，不是生产准确率，也不代表通过一例注入测试就能保证所有提示词攻击安全。

## 需修复的问题

### 1. 识别缺少应用已掌握的牌面状态

`buildIntentExtractionMessages` 只收到用户消息和场景，`hasExistingCards` 到 `createResponsePlan` 阶段才使用。真实模型不知道服务端已经掌握原牌，于是要求用户重新提供。应让提取层接收由服务端验证的牌面可用状态，明确牌面细节由后续解读阶段提供，避免把应用已知资料当作用户缺失信息。不能信任客户端自行声明的记录归属或原牌。

### 2. 澄清条件过宽

现有提示词中“缺失信息会改变回应”可能涵盖任何能增加个性化的细节。实际模型将岗位、行业、听众等都作为进入回应前的必填项。应区分改变核心任务或导致明显歧义的必要信息，与仅提升针对性的可选信息；明确对象、目标后允许先给有限范围的回应。必须保留二选一缺选项时的必要澄清。

### 3. 引用合法仍可能强化原意

换题样本把“我想用今晚两小时准备开场”概括为“只能用今晚两小时准备开场”。引用存在但从计划时间强化成硬性限制，说明结构和引用检查不能替代语义复核。应增加对程度、确定性及限制强度的样本评测。
