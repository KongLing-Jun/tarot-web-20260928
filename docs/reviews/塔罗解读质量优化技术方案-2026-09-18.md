# 塔罗解读质量优化技术方案

日期：2026-09-18

依据：用户提供的星币7每日一牌截图、后续补充的常规解读截图（“事情怎么看”，按过去／现在／未来组织）、当前项目源码 `aa6f0a2`、本轮检索的官方技术文档。

范围：分析与方案设计；未修改提示词、模型配置或业务代码，未安装第三方Skill，未调用付费模型进行对比实验。

## 1. 结论与优先顺序

**建议先改善输入背景、回答要求和评测，再决定换模型；使用轻量、可版本管理的塔罗知识包，不要先引入完整Agent框架、向量数据库或微调。**

当前问题不是“模型说得不够肯定”这么简单。应当提升的是：直接回答问题、解释为何这样判断、说明改变判断的条件、给出能执行的下一步。不能靠删除所有“可能”、强迫模型预测未来或猜测他人心理制造确定感。

用户补充的常规解读截图说明，问题范围不能限定在每日一牌。优化应覆盖首次牌阵解读、追问、重新生成与每日指引，共同检查回答是否切题、是否反复退回免责声明。每日牌缺背景只是其中一个分支的问题，不能作为整体体验不佳的统一解释。

| 优化方向 | 建议优先级 | 解决什么问题 | 不能单独解决什么 |
|---|---|---|---|
| 关键背景与意图识别 | P0 | 问题过宽、A/B选项不明、每日牌缺乏情境 | 模型遵循指令和中文表达能力 |
| 提示词重构与少量优质示例 | P0 | 开头绕弯、两边都说、反复免责声明、没有重点 | 缺失的真实信息 |
| 固定牌面语义评测 | P0 | 不知道修改是否真的变好 | 不能替代人工判断 |
| 塔罗知识／工作流包 | P1 | 牌义过短、牌位结合弱、多牌仅逐张复述 | 不能提供现实证据或保证预测准确 |
| 模型同题盲测与分层路由 | P1 | 复杂比较、长上下文、表达能力不足 | 同样不能弥补空输入和错误目标 |
| 结构化结果与定向修复 | P1，评测后决定 | 稳定呈现结论、依据与行动，检出缺项 | JSON格式正确不等于内容有价值 |
| 向量RAG、微调、多Agent | 暂缓 | 规模增长后的检索、稳定风格等专项问题 | 不应作为本次第一步 |

以上是结合项目现状的工程判断，不是已经测出的收益排名。

## 2. 两类截图反映的共同问题与差异

### 2.1 第一张：每日一牌

截图标题是“每日一牌 · 2026-09-17”，回复围绕星币7正位。这与“填写问题、选择牌阵、抽多张牌”的流程不同。

截图的优点：保留了等待、投入和收获的牌义，提出了记录投入的小步骤，也没有保证必然结果。

截图的不足：

- 用学习、项目、身体习惯等多个场景同时兜底，读者需要自己做一次翻译。
- “不能保证结果、不能判断坚持还是停”占据了重要篇幅，却没有把可执行的主张放在最前面。
- 所谓一个小步骤包含多项记录任务，认知负担不小。
- 正文更像解释“为什么不能替你判断”，而不是帮助读者判断下一步。

第一张截图本身只能反映每日牌样例；用户随后补充了常规解读截图，评估范围因此扩展。两张截图均不能确认生成时使用的模型和提示词版本。

### 2.2 第二张：常规解读“事情怎么看”

可见正文按“过去／现在／未来”组织，开头给出“从消耗走向休整”的总体概括。截图未显示原始提问、完整对话、实际牌名与方向，也没有展示全部正文，因此不能断言用户没有提供背景，不能核验牌面解释是否正确；仅凭这三个位置也不确认实际牌阵ID。

可见的具体问题：

| 截图表现 | 对体验的影响 | 优化方向 |
|---|---|---|
| 已有主张，但“担忧、反复想事、精神紧绷”“规则、经验、指导、传统路径”等词连续罗列 | 用户仍需自己把抽象词映射到事情 | 在已有事实上选出最相关的解释，说明其与问题的关系；没有背景时保持简短 |
| “不能把它写成你确实经历过焦虑或失眠”“不保证某件具体事一定成功，也不说明事情会停住” | 多次中断解读，正文显得不断撤回判断 | 保留事实边界，在必要处集中说明；逐牌不重复自我辩护 |
| “如果一直硬撑……愿意休息和沉淀……” | 条件仍是泛用建议，没有可核对的具体情境 | 有背景时给现实条件和反馈；无背景时不把硬撑等状态当作用户事实 |
| 到多段解释之后才问工作、感情、财务还是身心状态 | 先输出大量低针对性内容，再补关键问题 | 关键对象不明时，先给简短可支持的回应，并尽早提出一个真正改变答案的问题 |

这里需要区分两种根因，不能把责任直接归给用户输入：

1. **用户此前已经提供背景**：检查前端请求、Agent构建、服务端prompt、历史裁剪是否完整传入；若已传入，再检查模型是否忽略背景。增加输入表单不能修复上下文丢失。
2. **本次确实没有关键背景**：问题是澄清时机与回答篇幅。避免在未知具体事情的情况下，先生成长篇完整解读再到末尾询问领域。

当前公共提示词包含“不能把牌义写成经历”等规则，也包含类似否定式示范，与截图的表达形式相近。**可能存在把内部写作约束复述给用户的现象**，但在未取得该次请求与版本前，只能作为实验假设。正确方向是让模型遵守边界，同时用自然、简洁的方式提供解读，不是删除边界。

## 3. 当前实现审计

### 3.1 已确认事实

| 位置 | 当前情况 | 对优化的意义 |
|---|---|---|
| 私有服务端配置，由 `lib/api/server-config.ts:19` 读取 | 本机当前 `MODEL_ID=deepseek-v4-flash`，接口主机为 `api.deepseek.com` | 可以先保留现模型建立基线；本机配置不等于历史请求或生产配置 |
| `app/api/interpret/route.ts:299` | 使用Chat Completions；全部prompt放在一条user消息里，发送max_tokens和stream | 稳定规则与用户事实没有用消息角色分层；未显式控制thinking/effort |
| `lib/api/prompts.ts:17` | 已有事实边界、共情要求、直接回应要求和示例 | 并非“完全没做prompt工程”；不能直接丢掉已处理的防编造规则 |
| `lib/api/prompts.ts:68` | 六类牌阵已有各自分析规则 | 应在现有机制上改进，不另造一套不一致的解读链路 |
| `lib/api/prompts.ts:4` | 每张牌传入牌位名称、牌名、方向、关键词和短牌义 | 牌位描述和更细的情境知识没有在该函数中提供 |
| `app/daily/page.tsx:158`、`lib/api/prompts.ts:217` | 每日牌question为空；prompt明确没有个人背景、不要求先补问题 | 每日牌个性化上限低，不能期待它像已知具体问题的咨询 |
| `lib/interpretation-quality.ts:25` | 检测结构、牌名、方向、牌位；明确不评估语义质量 | “结构正确但空泛”会被接受 |
| `tests/interpretationCorpus.test.ts` | 已有六牌阵固定样本，并明确测试“事实错误仍可能通过规则校验” | 可以复用样本组织方式，增加真实模型输出评测 |
| `tests/browser/interpretation-empathy.mjs` | 使用固定测试回复检查展示契约 | 证明UI呈现，不证明模型实际解读质量 |
| `lib/agent/agentTurn.ts:442` | 重新生成要求更清晰具体、避免重复表达 | 未提供这次具体哪里失败，可能只得到换一种措辞的同类答案 |

### 3.2 尚待验证的原因

1. **背景缺失、传递丢失或未被利用**都可能导致泛化；每日牌可以从代码确认缺背景，常规牌阵的新截图只证明回答表现，不能证明原始输入为空。需对照脱敏的原始问题、请求、最终prompt和输出定位。
2. **通用约束较长、否定表达较多**，可能使模型把“不越界”表现为“处处保留”。这是待A/B验证的假设，不能凭prompt长度认定原因。
3. **少量示例偏向纠正过度推断**，有必要补充“信息充分时明确给倾向”的正例，避免只学会拒绝下判断。
4. **知识颗粒度粗**，可能使专业说明停留在牌义复述；需要对比扩充知识前后的输出。
5. **模型能力／推理配置**可能影响多牌综合，但本轮没有模型盲测，不给出“换某模型必然更好”的结论。

## 4. 优化目标：明确而有边界

将“模棱两可”拆成可评估的问题：

| 用户感受 | 不合格表现 | 希望得到的表现 |
|---|---|---|
| 没回答 | 重复问题、安慰后结束 | 前一至两段有与问题对应的主张或明确缺口 |
| 两边都能解释 | A有好处，B也有好处，自己决定 | 在用户重视的条件下给优先顺序；条件改变时说明如何调整 |
| 人人都适用 | 相信自己、保持平衡、顺其自然 | 结合本次事实、实际牌位与限制说明建议 |
| 没有做法 | 多沟通、多观察 | 对一个对象执行一个动作，并说明观察什么反馈 |
| 专业部分像字典 | 每张牌抄牌义，没有综合 | 解释牌位如何改变解读，以及两张关键牌的支持或张力 |
| 语气很肯定但没依据 | 一定复合、必定成功、他就是这样想 | 将象征解释与现实判断分开，不编造结论 |

信息不足时，**明确指出缺什么**也可以是好答案。质量目标不是“每次必须选A或B”。

## 5. 输入层：最少但关键的上下文

### 常规牌阵

优先复用现有问题输入，不强制新增长表单。建议支持可选补充：关注领域、希望解决的问题、时间范围、已发生的事实、现实限制。

- 二择一：先明确A和B分别是什么、用户最看重什么。选项身份缺失时可以要求补充后再抽牌；已抽牌则保留原牌，补充后继续解释。
- 求做法：明确已尝试的动作及反馈，避免重复建议。
- 关系：区分可观察行为与对方心理，不能用牌面证明后者。
- 倾诉：不强迫排序和行动，避免为追求“具体”违背用户意愿。

只在答案会因此改变时问一个关键问题；不每次都走澄清流程，也不自动从旧聊天中挖取私密背景。未来若使用历史，限定当前会话和用户明确允许的上下文。

针对第二张截图，先核查该次解读有没有正确接收用户已经提供的领域、事件和目标，再决定是否需要澄清。确实缺少关键对象时，把一个澄清问题放在简短回应之后，避免先写完整的多段泛用解释；已抽牌保持不变。用户明确希望不补背景直接阅读时，提供简洁的象征解读，不持续追问。

### 每日一牌

建议保留“直接看今日指引”，另提供可选的“今天想关注什么”短输入。用户跳过时明确定位为通用练习，避免假装个性化。

输入不能只增加一个未传入模型的前端字段：需要同时修改daily请求协议、服务端构建prompt、存储与缓存区分。同一天不同关注主题不能误命中同一份旧解读。

## 6. 提示词：减少兜底，增加可执行的回答要求

### 6.1 分层构建

建议服务端组装：

1. system层：事实边界、简洁中文、不能编造用户经历等稳定规则。
2. 任务层：daily／首次解读／追问／A-B比较等任务要求及必要示例。
3. 知识层：仅本轮实际牌、方向、牌位和相关解释方法。
4. user层：用户原话、明确事实及本轮补充，以数据边界标识，不赋予修改规则的权限。

当前agent模式允许客户端直接提交完整prompt。实施统一质量要求时，应逐步转为提交明确的任务类型和输入数据，由服务端生成prompt；同时兼容选阵决策、追问与重生成，不仅修改普通解读分支。

### 6.2 建议实验的核心规则草案

```text
先确定本轮任务：求判断、比较选择、求做法、理解处境、倾诉、每日通用指引。

需要判断或选择时，先给当前信息支持的倾向及适用范围。
若关键事实不足，直接说明最关键的缺口；不要罗列许多互相抵消的可能。

用已知事实说明建议为何适用。用牌位和牌义说明观察角度，不能把牌面当作现实证据。
如果牌的象征倾向与现实限制有张力，优先尊重现实限制，并解释张力。

需要行动时给一个动作及可观察反馈；除非用户要求，不把多个任务装成“一件小事”。
用户不需要建议时省略行动。

只有会改变判断的条件才写进正文，不反复解释塔罗的局限。
避免无关场景串举。给出建议后，不再用泛泛的“最终还是看你自己”撤回建议。
不能承诺未来结果、虚构概率或断言他人内心。
```

这只是实验草案，应与现有约束合并、去重，并保留现有章节协议。第一阶段不同时更换prompt和前端解析器，以便分辨效果来源。

### 6.3 增加平衡的few-shot示例

至少覆盖：信息充分的选择题、信息不足的选择题、仅倾诉、具体执行问题、多轮纠正、每日无背景指引，以及常规时间牌阵中“已有背景被忽略”和“确实缺少背景”两类反例。每例标明输入、实际牌位、优质回复与评语。不要把一段“很有感觉”的通用回复反复塞进所有请求。

提示词和示例属于受控产品资产，保存版本号；以后发现失败样本，先归入已有错误类别再改规则，而不是不断追加针对单个用户的禁令。

## 7. 是否需要塔罗Skills：需要内容模块，不必先安装插件

**在Codex里安装一个Skill，不会自动被线上DeepSeek请求加载。** 当前代码只发送自己构造的messages，没有Skill发现、读取、注入流程。

Agent Skills通常将任务说明、参考资料和工具组合起来；不同运行环境有不同加载机制。Claude官方API的Skills机制依赖其容器与工具接口，不能当成现有Chat Completions请求的通用参数。参见[Agent Skills官方说明](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)。

### 推荐：服务端可控的轻量知识包

```text
lib/tarot/knowledge/
  cards/            # 按cardId组织；正逆位、意象、领域视角、常见误读
  spreads/          # 六类牌阵的牌位职责、综合顺序与比较方法
  methods/          # 逆位解释、多牌张力、现实事实与象征的区分
  examples/         # 经人工审核、带牌位与情境的少量好例子
  manifest          # 内容版本、适用牌系、来源、许可、审核信息
```

这些是建议目录，不是已新增的实现。初版优先扩充常见失败案例涉及的牌，不必一次写完全部素材。

每张牌增加：核心象征、正／逆位解释分支、各牌位的解释重点、常见错误、与领域相关的可观察问题。逆位不能一律等于坏事；领域例子不能直接冒充用户经历。

**检索方式：** 当前只有78张牌和6种牌阵，按cardId、方向、spreadId精确查表最简单。以固定ID注入当次牌义，按意图选择少量示例。除非后续资料规模确实扩大且评测发现查表不足，否则无需向量数据库。

**内容质量：** 选定一致的牌系；由具备塔罗知识的编辑审核。资料保留来源与使用许可，避免直接复制来源不明的整本牌义。外部Skill如要采用，先审查内容及脚本，不让其自动联网、修改数据或执行无关工具。

**重要边界：** 知识包提升解读体系的一致性与可解释性，不产生对现实事件预测有效性的证据。

## 8. 模型选择与参数策略

### 8.1 先评当前模型，再评升级

建议候选：

| 实验组 | 设置 | 用途 |
|---|---|---|
| A 基线 | 当前配置模型＋当前prompt | 记录现状 |
| B prompt改进 | 同模型＋新回答规则与示例 | 单独测prompt收益 |
| C 知识增强 | B＋按ID加载的知识包 | 单独测知识收益 |
| D 模型升级 | 同一改进输入＋DeepSeek当前可用Pro候选 | 测更强模型是否值得 |
| E 可选跨厂商 | 同一输入＋业务可用的OpenAI/Claude候选 | 在预算、地域可用性和数据处理约束满足后比较 |

不按厂商通用榜单直接判断哪家“最会塔罗”。本产品更在意中文自然度、回应针对性、牌位综合、事实边界、延迟和成本。

### 8.2 当前DeepSeek配置需要特别注意

本机模型名是`deepseek-v4-flash`。本轮检索到官方历史发布记录使用该名称，而当前Chat Completions参考页列出`deepseek-flash`及`deepseek-v4-pro`。这表明文档存在名称演进；**不能据此断言当前别名已失效，也不要自动改名**。实施前用当前账号可用模型清单及小规模兼容请求确认，记录请求模型、响应模型和时间。参见[发布记录](https://api-docs.deepseek.com/updates/)与[Chat Completions参考](https://api-docs.deepseek.com/api/create-chat-completion/)。

当前代码未发送thinking或reasoning_effort，不等于没有推理模式。官方当前说明默认开启思考；思考模式下temperature不生效。因此“把温度调低就更准确”不是本项目可直接采用的结论。应先明确模式，再分别测输出质量、可见正文首字延迟和总耗时。参见[DeepSeek思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)。

模型、模式、token预算、重试策略和超时均走服务端配置，不散落在各页面。复杂多牌或长追问是否用高推理强度，必须由评测决定；不为所有每日牌默认使用最昂贵配置。

### 8.3 成本与路由

不在本方案中虚报单次价格。上线前按供应商当时价格计算：输入token费用＋输出token费用＋适用的推理费用＋重试费用。区分缓存命中并记录实际usage。

可考虑简单每日牌走低成本档、复杂比较走较强档，但初期直接使用同一模型完成实验即可。只有收益和成本数据支持时再加路由，避免过早增加故障面。

## 9. 输出结构与质量控制

### 第一阶段：继续使用当前Markdown与SSE

沿用核心解读、行动建议、专业说明的现有解析与渲染。把“主张明确、有事实依据、条件具体”加入评测，不再额外堆标题。专业说明应含全部真实牌位，但核心回答不能靠展开专业说明才能读懂。

### 第二阶段：评测证明需要时再结构化

可定义内部结果字段：`answer`、`stance`、`factRefs`、`cardRefs`、`conditions`、`nextAction`、`clarifyingQuestion`、`cardExplanations`。其中行动和澄清允许为空；stance表示建议立场，不是成功概率。

引用ID必须能对应服务端的用户事实和抽牌记录，不能让模型生成无法核对的来源。该结构保存简短依据，不要求暴露模型内部思考过程。

支持严格schema的供应商可以减少结构错误，但不能保证事实正确或建议质量。参见[Structured Outputs说明](https://developers.openai.com/api/docs/guides/structured-outputs)。DeepSeek的JSON模式也需要服务端解析与校验；JSON合法不等于满足本产品字段和语义。参见[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。

**流式取舍：** 不应直接把未完成的JSON交给现有Markdown渲染器。先做独立适配和兼容测试，再决定缓冲完整结构还是采用可验证的分段事件；保留取消、断流恢复与旧历史兼容。

### 语义质检与重生成

- 确定性规则继续检查牌位、方向、缺牌与结构。
- 离线语义评分检查是否答题、是否具体、是否自相矛盾、是否编造事实。
- 稳定后可给复杂请求增加抽样在线质检，或仅在用户反馈“太泛”时定向修复。
- 修复请求附上具体问题，例如“没有比较用户提到的通勤成本”，不是仅要求“更具体”。保留原问题、原牌、原方向，不重抽。
- 自动修复次数应有配置上限和费用预算；不要无限重试。若正文已流给用户，不在后台悄悄替换内容，应提供明确的新版本。

## 10. 评测设计与验收标准

官方评测建议以真实任务构造数据集、持续回归，并用成对比较或清晰评分规则评估；模型裁判需要校准，防止偏好较长答案和位置偏差。参见[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。以下为本项目拟定方案。

### 数据集

建议先做60条开发集＋30条独立留出集，属于计划规模而非已完成数据。覆盖六种牌阵、每日牌、追问纠正、信息充分与不足、只倾诉、拒绝行动、相互冲突的条件以及指令注入样例。

同一测试例固定问题、背景、牌阵、牌位、方向和历史。开发集用于改prompt，留出集不得提前看答案调规则。每个实验组先重复生成2次观察波动；如预算不够，先缩小模型候选而非把不同随机牌面对比当作模型收益。

补充截图应作为“重复免责声明、澄清过晚、解释抽象”的质性失败案例。取得原始问题与实际牌面后才转换成可复现的模型评测用例，不从截图臆造抽牌结果。常规牌阵至少增加一组配对测试：同一牌面分别输入简短问题和包含具体事实的问题，检查后者是否实质利用事实，而非仅复述领域名称；同时检查背景在首次解读、追问与重新生成链路中是否保留。

### 评分表

| 维度 | 0分 | 1分 | 2分 |
|---|---|---|---|
| 直接回应 | 未回应 | 有回应但绕弯 | 开头给出明确主张或关键缺口 |
| 情境针对性 | 人人适用 | 提及背景但关联弱 | 建议实质依赖已知背景 |
| 判断与条件 | 两边都说／无依据断言 | 有立场但依据不全 | 有立场或明确不足，条件可核对 |
| 牌位综合 | 错牌或复述词典 | 单牌结合问题 | 多牌关系与现实限制均解释清楚 |
| 行动适配 | 空泛／违背用户意愿 | 可做但笼统 | 单一具体动作和反馈；不需行动时适当省略 |
| 表达效率 | 重复、套话多 | 基本清楚 | 简洁自然，不反复撤回结论 |

事实捏造、牌面错配、违背用户明确意图单独作为严重错误统计，不靠总分掩盖。倾诉题和每日无背景题设置不同评分预期，避免奖励模型强行给建议。

### 建议上线门槛（待团队确认）

- 固定留出集的牌名／方向／牌位匹配100%；这只是测试集目标，不是承诺线上零错误。
- 新版本成对盲评胜率至少65%（平局单列），且两个评分人分歧有复核记录。
- 严重编造事实与违反明确用户意图的比例不高于基线；发布集出现严重案例先处理再发布。
- “直接回应”“针对性”平均分提升，不以答复变长冒充改善。
- 记录正文首字延迟与总延迟的P50/P95、平均token及单次费用；先建立基线，再由业务设预算，不凭空设绝对秒数。

上述比例是建议验收阈值，不是本轮测得结果。小样本报告需同时给出样本数与不确定性，不用胜率单一数字宣称普遍优势。

## 11. 对截图回复的改写示例

以下为人工起草的效果目标，**不是模型实测结果，也不用于替换真实生成逻辑**。

### 每日牌，没有个人背景

> 星币7正位给今天的提示是：先检查已有投入的进展，再决定要不要继续加码。
>
> 今天选一件正在推进的事，查看一个能说明进展的事实，例如最近一次反馈。暂时没结果时，先区分“还没到反馈时间”和“已经有具体问题”，两者需要的下一步不同。
>
> 这张牌适合提醒你评估投入，不要求你一味坚持，也不替你决定放弃。

仍然是通用指引，但主张先出现，场景范围收窄，避免连续列举学习、工作、身体等所有情况。

### 有具体背景的示范

虚构输入：“我练琴三周，每天半小时，录音里节奏还是不稳，想再把每天时间加倍。”同为星币7正位。

> 先别把练习时间加倍，优先确认现在的练法有没有改善节奏。你已经保持了三周投入，眼下要评估的是方法的反馈，而不是单纯增加时长。
>
> 下一次练习只挑一段总是失稳的乐句，放慢到能稳定完成的速度练习，并听这一段的录音是否更稳。星币7提供的对应角度是“检查投入与收获”，这里的建议则依据你已经投入时间、但节奏问题仍在的描述。

这个例子展示“事实→建议→反馈”的结构，不证明塔罗能判断练琴效果。实际产品需根据用户领域调整，不能照抄固定动作。

### 第二张截图：只针对可见表达的改写目标

缺少原始问题与牌面，不能重新进行一次具体占卜。以下仅演示如何缩短截图已有的总体解释；假设本次确实未提供领域，才适用末尾的提问：

> 这组牌的象征主题是：先整理和恢复，再考虑加速推进。它更适合用来检查推进节奏，尚不足以回答某件事最终会不会成功。
>
> 你这次最想看清的是哪件具体的事？

这段不是最终解读模板。用户如果已经说清具体事情，应直接结合那些事实回应，不能重复询问。重点是用简短的解读承接一个关键问题，避免先罗列三大段抽象词，再补问工作、感情、财务等领域。
